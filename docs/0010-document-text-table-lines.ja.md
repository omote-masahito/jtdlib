# RFC 0010: DocumentText 表の物理行と論理セルの再構成

Status: draft

Observed: 2026-09-09

English version: [0010-document-text-table-lines.md](0010-document-text-table-lines.md)

拡張対象: RFC 0003 (DocumentText), RFC 0009 (段落レコード構造)

## 概要

RFC 0009 が「段落/行ヘッダー」と呼ぶ `0x0010` レコードと「表セルヘッダー」`0x0030` レコードについて、次の点を新たに観測した。

1. `0x0010`/`0x0030` は表の論理行・論理セルではなく、**物理行**とそこに現れる**セル断片**を表す。複数行にわたるセルは物理行ごとの断片に分割して格納され、断片を縦に結合したものが論理セルである。
2. `0x0010` レコードの `w4` はフラグ語で、それ以降の本体は `(tag, len, payload…)` 形のサブエントリ列である。表の行スペックはサブエントリ `0x008f` の中にあり、`w4` 自身が `0x008f` とは限らない。
3. 行スペック中の各罫線スパンは「そのスパンの**下**に罫線があるか」を表す。これが論理セルの縦方向の境界を決める。
4. 罫線配置が直前の物理行と同一のとき `0x0010` レコードは省略され、その物理行は `0x0030` 断片と終端 `0x000e` だけになる。
5. サブエントリ `0x0026` は段落インデントで、`payload[1]` が段落左端、`payload[3]` が先頭行の絶対位置（単位: カラム）。
6. 本文中の `0x000c` は改ページ、`0x0009` はタブ。
7. 表座標空間（`0x0030` の `b0`/`b1`、行スペックの幅）の単位は**1 文字幅の 1/4**。

再構成の結果は、一太郎2023（Ver.33）で作成した合成文書 11 本と、行政機関がインターネットで公開している一太郎文書 9 本（1990 年代〜2020 年代の様式）について、一太郎自身のテキスト保存（罫線内文字列＝セル単位、形式 10）と照合した。空でないセル文字列はすべて一致する。セルの列挙順は常には一致しない（Known Gaps 参照）。

## 用語

- **物理行 (physical line)**: 画面上の 1 行。省略可能な `0x0010` レコードで始まり、`0x000e` で終わる。
- **断片 (fragment)**: 1 つの物理行に現れる 1 セル分のテキスト。`0x0030` レコードで始まる。
- **論理セル (logical cell)**: 同じ列範囲の断片を縦に結合したもの。ODT 書き出しの `table:table-cell` に対応する。

## 0x0010 レコードのサブエントリ構造

RFC 0009 のレコードレイアウト（`w0=0x001c, w1=class, w2=len, …, フッター`）はそのまま成立する。`w3` は常に `0x0000`、`w4` はフラグ語で、観測値は次のとおり。

| w4 | 意味（推定） |
| --- | --- |
| 0x0000 | 属性なし段落 |
| 0x0002 | 古い文書での表行（本体に `0x008f` サブエントリを含む） |
| 0x0020 | 属性付き段落（本体に `0x0004` サブエントリを含む。タブ位置か） |
| 0x0024 / 0x0026 / 0x002a | 段落属性の組合せ（本体に `0x0026` サブエントリ＝インデントを含む） |
| 0x008f | 一太郎33 が生成した表行 |
| 0xffff | 終端 |

`w4` の直後から `0xffff` までがサブエントリ列である。多くのサブエントリは `(tag, len, payload[len])` の形をとる。

```text
001c 0010 001c 0000 0002  0003 0000  0062 0000  008f 000b 00c4 0000 0002 0008 0020 0008 0003 0008 0098 0000 0002  ffff  001c 0000 0010 001f
                          ^tag 0003 len 0     ^tag 0062 len 0   ^tag 008f len 11: 行スペック
```

サブエントリ `0x0004`（`0004 0009 0320 0009 0320 …`）はこの形に当てはまらず、未解読である。実装上は `0x008f` と `0x0026 0x0005` をタグで探索すれば十分である。

### サブエントリ 0x0026 — 段落インデント（decoded）

```text
0026 0005 [a] [left] [b] [first] [c]
```

| フィールド | 意味 | 根拠 |
| --- | --- | --- |
| left | 段落左端インデント（カラム） | マクロ `Indent(1, 2, 0, 0, 0, 101)` → `left=2, first=2` |
| first | 先頭行の絶対インデント（カラム） | マクロ `Indent(1, 0, 0, 1, 0, 101)` → `left=0, first=1` |
| a, b, c | 観測範囲では常に 0 | |

RFC 0009 の `w10` はこの `left` に相当する。根拠は `Indent` マクロでインデントを設定した合成文書である。RFC 0009 は一部のサンプルで `w7` が視覚的なインデントではなく段落スタイル ID のように振る舞うと観測している。このフィールドが、名前付きスタイル由来か直接指定かを問わず段落に解決されたインデント値を持つのであれば両者は両立するが、これは未証明である。

### サブエントリ 0x008f — 表の行スペック（decoded、一部 partial）

```text
008f [len] [width] 0000 [fmt] [span…]        (ffff は 0x0010 レコード全体の終端)
```

| フィールド | 意味 |
| --- | --- |
| width | 表全幅（表座標単位） |
| fmt | スパン列の形式。0 と 1 は 4 ワード固定、2 は可変長 |
| span | 左から順に並ぶ罫線スパン |

スパンの形式:

- fmt 0/1: `(tag, 0x0000, style, width)` の 4 ワード。
- fmt 2: 上記に加え、`tag ∈ {0x0008, 0x0000}` のとき `(tag, width)` の 2 ワード。`0x0008` は style `0x08`、`0x0000` は style 0 と等価。

`style` の観測値は `0x00`（下罫線なし）と `0x08`（下罫線あり）、および古い文書での `0x24`, `0x14` など（罫線種を含むと推定。0 か非 0 かだけを用いる）。`tag` の観測値は `0x13`, `0x1b`, `0x23`, `0x27`, `0x2b` などで、`tag & 0x08` は常に `style & 0x08` と一致する。

スパンの位置は表の左端からの累積で決まる:

```text
x(k) = origin + Σ_{j<k} (width_j + gap)     gap = 2 (fmt 2) / 0 (fmt 0, 1)
```

- 先頭の余白列（例: `(0,2)` の空セル）はスパン列に含まれない。
- 幅 0 のスパンが現れることがあり、位置を占めない。
- `origin` は文書によって異なる（観測値: 2, 4, 6）。参照実装では断片座標と一致する原点を総当たりし、最も多くの断片を覆うものを採用する。

断片 `(x0, x1)` を覆うスパンは `x(k) ≤ x0 < x(k) + width_k` を満たすものである。

RFC 0009 はそのサンプルでセル間ギャップを 4 単位と報告しているが、本 RFC の合成文書では 2 単位（`(2,58) (60,116)`）である。ギャップは表の罫線・余白設定に依存し、定数ではない。

## 0x0030 レコード（12 ワード固定）

```text
001c 0030 000c 0000 [x0] [x1] 00ff [flag] 000c 0000 0030 001f
```

RFC 0009 の `b0`, `b1` がそれぞれ `x0`, `x1` で、断片の左右端座標。`flag` は一太郎33 でセル内に改行を挿入したとき `0x0002` が観測されたが、古い文書では常に 0 で、論理セルの結合には使えない。

表の右端に幅 ≤ gap の空断片（例: 全幅 120、最後のセルが 116 で終わる表での `(118,120)`）が現れることがある。これは右罫線の位置を占めるだけでセルではない。同じ表でも物理行によって現れたり現れなかったりする。

## 論理セルの再構成アルゴリズム

物理行 `L_i` の断片 `c` について:

1. 直前の物理行 `L_{i-1}` に同じ `(x0, x1)` の断片 `c'` があり、
2. `c'` を覆うスパンの `style` が 0（下罫線なし）であれば、

`c` は `c'` と同じ論理セルの続きである。それ以外は新しい論理セルを開始する。

`L_i` に `0x0010` レコードがない場合、各断片の `style` は `L_{i-1}` の同座標の断片から引き継ぐ。

古い文書では横罫線が独立した物理行（該当列に断片がない行）として現れることがあり、その場合は条件 1 で自然に切れる。

## セルの文字列化

断片のテキストは末尾の `0x000a` の有無で意味が変わる:

- `0x000a` あり: 段落終端。
- `0x000a` なし: ソフト改行。同じ論理セルの次の断片へ文字が続く。

一太郎のテキスト保存（罫線内文字列＝セル単位、改行置換文字 `R`）は、論理セルを次の規則で 1 行にする:

1. 断片を順に連結し、`0x000a` を `R` に置換する。
2. 最後の断片が `0x000a` で終わっていればその `R` は出力しない。終わっていなければ末尾に空段落があるものとして `R` を 1 つ出力する。
3. 先頭の空段落（テキストのない段落。図アンカーのみの段落を含む）は出力しない。

例（`gov-a.jtd`）:

```text
断片:  「商号(名  称)」+0x000a  /  「」           → 商号(名  称)R
断片:  「 印紙貼付欄」+0x000a                      →  印紙貼付欄
断片:  「ないでここに貼ってく」 / 「ださい。」+0x000a → ないでここに貼ってください。R
```

## ODT 書き出しとの対応

`SaveDocument(…, 22)` で得られる ODT の `table:table-row` は論理行、`table:table-cell` は論理セルに対応する。`gov-d.jtd` では `住所又は勤務先`（r1）と `（電話　－　）`（r2）が別の `table:table-row` であり、DocumentText では両者が同じ座標 `(44,144)` の断片として物理行 8〜11 に連続する。物理行 8 のスパンはすべて `style=0x08`、9〜10 は `0x00` で、上記アルゴリズムで両セルが分離される。`rowspan` は観測範囲では使われていない。

同一文書内でも ODT の列幅（cm）と DocumentText の座標は比例しない（`gov-d.jtd`: 30 単位 = 3.11 cm、16 単位 = 1.94 cm）。座標単位は物理長ではなく文字グリッドである（次節）。

## 表座標の単位（decoded、`synth-11-table-30col.jtd`）

1 行の文字数を 30 に設定した文書で 2×2 の表を作ると全幅 120、セル `(2,58) (60,116)` となり、既定の 40 字/行では全幅 160、セル `(2,80) (82,158)` となる。座標は文字数に比例して縮むので、単位は**1 文字幅の 1/4**（1 字 = 4 単位。罫線と余白は各 2 単位 = 半文字）である。一太郎の表は文字グリッド上に置かれるので、この単位で列幅を文字数に換算できる。RFC 0009 の「座標値の物理単位」の gap はこれで解ける。

## 0x0001 インラインレコードのセレクタ（追加）

RFC 0003 は selector `0x0003` をルビ親字とするが、実文書ではルビのない `電子証明書発行申請書`、`会社法人等番号` のような見出し・均等割付語にも付く。`0x0003` は「装飾付き本文」の一般形で、直後に selector `0x0082` のレコードが続く場合にのみルビ親字となる。selector `0x0000`/`0x0001` で内容が制御コード 1 文字（`0x0002`, `0x0008`）のものは図・枠のアンカーであり、本文には含めない。

## LayoutBoxText と Footnote ストリーム

`LayoutBoxText`（レイアウト枠＝テキストボックスの本文）と `Footnote`（脚注本文）は `DocumentText` と同じ `SsmgV.01` 形式で、ヘッダ w[5]（`0000 000a` の下位語）がセグメント数、以降に `TextV.01` + 領域長 + 領域 のセグメントがその数だけ並ぶ。

| ストリーム | セグメント数 | 領域の内容 |
| --- | --- | --- |
| DocumentText | 1 | 本文 |
| LayoutBoxText | 枠の数（`gov-c`: 10 = ODT の `draw:text-box` 数） | 枠ごとの本文。段落・表レコードは本文と同一形式 |
| Footnote | 1 | 脚注本文。脚注のない文書では selector 0x0001 のインライン "Note"（雛形のプレースホルダ）のみ |

セグメントの区切りは `TextV.01` マジックの走査で決まり、領域長は本文と同じく UTF-16 ユニット数（レコード含む）。`TextV.01` の直後 2 ワードが領域長である。各セグメントは RFC 0009/0010 の段落・表パーサーをそのまま適用できる。`gov-c.jtd` の 10 枠すべてで、ODT の `draw:text-box` の段落テキストと一致した（空行とタブを除く比較。表を含む枠では ODT 側が表セルを段落として列挙するため、空行数は一致しない）。

一太郎のテキスト保存（形式 10）にはレイアウト枠の本文は含まれない。枠のアンカーは本文中の selector 0x0001 インライン（内容 `0x0002`）と `LayoutBox` ストリームにあると推定されるが、対応付けは未解読。

selector 0x0001 のインラインは本文中では脚注番号（`*1`）などの自動生成テキストとしても現れ、一太郎のテキスト保存にも出力される。したがって 0x0001 を一律に非表示にはできず、Footnote ストリーム末尾の "Note" エントリだけを特別扱いする。

### Footnote ストリームのエントリ構造（decoded、`synth-09-footnote-single.jtd`）

一太郎2023 の GUI で脚注を 1 つ付けた文書で観測:

```text
本文 (DocumentText):
  …後述）  [001c 0000 …]  [001c 0001 0007 0000 0000 0001 001d] *1 [001e 0005 0000 0001 001f]  。 000a

Footnote:
  [001c 0000 …] [001c 0001 … 0001 001d] *1 [001e …] 用語物理行 (line): … 対応する。 000d
  [001c 0000 …] [001c 0001 … 0001 001d] Note [001e …]  (雛形の既定エントリ、000d なし)
```

- 本文側の脚注番号は selector 0x0001 のインラインで、直前に class 0x0000 のコンテキストマーカーがある。
- Footnote ストリームの 1 エントリは「`0x0000` マーカー → `0x0001` インライン（番号。本文側と同じ文字列）→ 本文 → `0x000d`」。`0x000d` はエントリ終端で、本文ストリームには現れない。
- 末尾に雛形由来の "Note" エントリが常に残る（脚注のない文書でも存在する）。
- 本文側マーカーと脚注エントリの対応は番号文字列で取れる。明示的な対応表は `FootnoteLink` ストリームにある（次節）。

### FootnoteLink ストリーム（decoded、`synth-10-footnote-multi.jtd`: 3 ページに脚注 5 件）

```text
ヘッダ 6 ワード: 0001 0001 0000 [size] [count] 0000
エントリ 15 ワード × count:
  001a  next  prev  0000  pos  ffff  ffff  0100  next  prev  num  page  index  ffff  next
```

| フィールド | 意味 |
| --- | --- |
| pos | 本文領域内での脚注マーカー（`0x0000` コンテキストレコード）の位置（ワード） |
| num | ページ内の通し番号（1 始まり）。本文の脚注番号 `*1`, `*2` と一致 |
| page | ページ番号（0 始まり） |
| index | 文書全体での通し番号（0 始まり） |
| next/prev | 前後のエントリ索引（0 始まり、端は `ffff`） |

観測: `pos` = 0x0291, 0x043d, 0x062f, 0x07af, 0x08bb がそれぞれ本文中の `[001c 0000 …]` マーカー直前の位置と一致する。ページごとに番号を振り直す設定では `num` が 1,1,2,1,2 となり、本文の `*1,*1,*2,*1,*2` と対応する。Footnote ストリーム内の各エントリ先頭の `0x0000` レコードにも文書通し番号（0x0000, 0x0001, …）が入る。

## RFC 0009 への影響

- 「座標値の物理単位」: decoded（1 文字幅の 1/4）。
- 「`0x0010 w4=0x008f` のサブエントリ `[tag, v1, v2, v3]` の式は未解読」: `v3` はスパン幅、`v2` は style（下罫線）、位置は上記のとおり累積する。サブエントリ数が `n_cells − 1` になるのは最後のセルの下に罫線がない場合だけで、一般にはスパン数である。
- 「`0x000a` decoded:false」: 段落終端として decoded。
- 「`0x0000 len=12` がルビ/インラインの直前に現れる」: 矛盾しない。同じ `0x0000` レコードが脚注マーカーのインラインの直前にも現れる。
- RFC 0009 の `w7`/`w10` の議論とは矛盾しない。サブエントリ `0x0026` の節の注記を参照。

## Known Gaps

- 一太郎のセル単位書き出しにおけるセルの**列挙順**。行→列の単純な順ではなく、未解読。本文テキストの抽出には影響しない。行政文書 9 本のうち 3 本は順序まで一致し、残りは空でない文字列の多重集合として一致する。
- fmt 1 のスパン列（`gov-a.jtd` に `0x14`, `0x16`, `0x24`, `0x27` のタグを持つ 4 ワード組が現れる）は原点総当たりで結果的に正しく対応づいているが、構造の独立した確認はできていない。
- サブエントリ `0x0004` の意味。
- `0x0030` の `flag` の意味。
- `0x0026` のインデントと RFC 0009 の段落スタイル仮説の関係。
- `Frame` ストリームと、レイアウト枠のアンカー対応。

## 検証方法

一太郎の COM（`JXW.Application` の `Application.Run(マクロ文, 3)`）で同一文書を `.jtd`, `.jtdc`, テキスト（セル単位）, ODT に書き出し、リーダーの出力をテキスト保存（空でない文字列の多重集合。可能な文書では順序まで）および、`LayoutBoxText` については ODT と比較した。合成文書は同じインターフェースからマクロで生成した。

本 RFC を実装した独立の純 Python リーダー（`jtdlib`: OLE コンテナ、`.jtdc` 展開、段落・表・脚注・レイアウト枠の解析）と、コーパス生成・検証スクリプトは別途公開する。

解析、リーダー、本文書は、著者が Anthropic の Claude と対話しながら作成した。観測、一太郎による正解データの生成、
検証は著者が実施・確認した。本 RFC の内容は一太郎やフィルターのソースコード、逆コンパイルに由来しない。
