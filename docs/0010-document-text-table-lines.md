# RFC 0010: DocumentText Table Physical Lines and Logical Cell Reconstruction

Status: draft

Observed: 2026-09-09

Japanese translation: [0010-document-text-table-lines.ja.md](0010-document-text-table-lines.ja.md)

Extends: RFC 0003 (DocumentText), RFC 0009 (paragraph record structure)

## Summary

This RFC records new observations about the class `0x0010` record that RFC 0009
calls the "paragraph / line header" and the class `0x0030` record it calls the
"table cell header":

1. `0x0010` and `0x0030` describe **physical lines** and the **cell fragments**
   that appear on them, not logical table rows and cells. A cell spanning
   several lines is stored as one fragment per line; the logical cell is the
   vertical concatenation of those fragments.
2. `w4` of a `0x0010` record is a flag word. The payload after it is a sequence
   of sub-entries of the form `(tag, len, payload…)`. The table row
   specification lives in sub-entry `0x008f`; `w4` itself is not necessarily
   `0x008f`.
3. Each border span in the row specification says whether there is a rule
   **below** that span. This is what decides the vertical boundary between
   logical cells.
4. When the border layout of a physical line is identical to the previous one,
   the `0x0010` record is omitted; the line then consists of `0x0030` fragments
   and the `0x000e` terminator only.
5. Sub-entry `0x0026` carries paragraph indentation: `payload[1]` is the left
   edge of the paragraph and `payload[3]` the absolute position of the first
   line, both in columns.
6. `0x000c` in body text is a page break; `0x0009` is a tab.
7. The unit of the table coordinate space (`0x0030` `b0`/`b1`, row-spec widths)
   is **one quarter of a character width**.

The reconstruction was checked against Ichitaro's own plain-text export
("text with cell strings", format 10) for 11 synthetic documents created with
Ichitaro 2023 (Ver.33) and 9 Ichitaro documents published on the web by
Japanese government bodies (forms from the 1990s to the 2020s). All non-empty
cell strings match; the enumeration order of cells does not always match (see
Known Gaps).

## Terminology

- **Physical line**: one line as displayed. Starts with an optional `0x0010`
  record and ends with `0x000e`.
- **Fragment**: the text of one cell as it appears on one physical line. Starts
  with a `0x0030` record.
- **Logical cell**: the vertical concatenation of fragments that share a column
  range. Corresponds to `table:table-cell` in the ODT export.

## Sub-Entry Structure of the 0x0010 Record

The record layout of RFC 0009 (`w0=0x001c, w1=class, w2=len, …, footer`) holds
unchanged. `w3` is always `0x0000`. `w4` is a flag word; observed values:

| w4 | Meaning (hypothesis) |
| --- | --- |
| 0x0000 | Paragraph without attributes |
| 0x0002 | Table line in older documents (payload contains a `0x008f` sub-entry) |
| 0x0020 | Paragraph with attributes (payload contains a `0x0004` sub-entry, possibly tab stops) |
| 0x0024 / 0x0026 / 0x002a | Combinations of paragraph attributes (payload contains a `0x0026` sub-entry = indentation) |
| 0x008f | Table line generated by Ichitaro 33 |
| 0xffff | Terminator |

The words after `w4` up to `0xffff` form the sub-entry list. Most sub-entries
have the shape `(tag, len, payload[len])`:

```text
001c 0010 001c 0000 0002  0003 0000  0062 0000  008f 000b 00c4 0000 0002 0008 0020 0008 0003 0008 0098 0000 0002  ffff  001c 0000 0010 001f
                          ^tag 0003 len 0     ^tag 0062 len 0   ^tag 008f len 11: row specification
```

Sub-entry `0x0004` (`0004 0009 0320 0009 0320 …`) does not follow this shape and
is not decoded. For an implementation it is sufficient to scan the payload for
`0x008f` and for `0x0026 0x0005`.

### Sub-Entry 0x0026 — Paragraph Indentation (decoded)

```text
0026 0005 [a] [left] [b] [first] [c]
```

| Field | Meaning | Evidence |
| --- | --- | --- |
| left | Left indentation of the paragraph, in columns | Macro `Indent(1, 2, 0, 0, 0, 101)` → `left=2, first=2` |
| first | Absolute indentation of the first line, in columns | Macro `Indent(1, 0, 0, 1, 0, 101)` → `left=0, first=1` |
| a, b, c | Always 0 in the observed range | |

`w10` of RFC 0009 corresponds to `left` here. The evidence is a synthetic
document in which the indentation was set through the `Indent` macro; RFC 0009
observed that `w7` in some samples behaves like a paragraph-style identifier
rather than a visual indent. Both observations may be true at once if the
field holds the resolved indentation of the paragraph regardless of whether it
comes from a named style or from direct formatting; this is not proven.

### Sub-Entry 0x008f — Table Row Specification (decoded, partially)

```text
008f [len] [width] 0000 [fmt] [span…]        (ffff terminates the whole 0x0010 record)
```

| Field | Meaning |
| --- | --- |
| width | Total width of the table, in table coordinate units |
| fmt | Span list format. 0 and 1 are fixed 4-word spans; 2 is variable length |
| span | Border spans from left to right |

Span forms:

- fmt 0/1: `(tag, 0x0000, style, width)`, 4 words.
- fmt 2: in addition to the above, `tag ∈ {0x0008, 0x0000}` gives a 2-word span
  `(tag, width)`; `0x0008` is equivalent to style `0x08`, `0x0000` to style 0.

Observed `style` values are `0x00` (no rule below) and `0x08` (rule below), plus
`0x24`, `0x14` and similar in older documents (presumably including the line
kind; only zero versus non-zero is used). Observed `tag` values include `0x13`,
`0x1b`, `0x23`, `0x27`, `0x2b`; `tag & 0x08` always equals `style & 0x08`.

Span positions accumulate from the left edge of the table:

```text
x(k) = origin + Σ_{j<k} (width_j + gap)     gap = 2 (fmt 2) / 0 (fmt 0, 1)
```

- A leading margin column (for example an empty cell at `(0,2)`) is not
  represented in the span list.
- Spans of width 0 occur and occupy no position.
- `origin` differs between documents (observed: 2, 4, 6). The reference
  implementation tries every origin that aligns with a fragment coordinate and
  keeps the one that covers the most fragments.

The span covering a fragment `(x0, x1)` is the one with `x(k) ≤ x0 < x(k) + width_k`.

RFC 0009 reports 4-unit gaps between cells in its samples; the synthetic
documents in this RFC show 2-unit gaps (`(2,58) (60,116)`). The gap is a
property of the table's border and margin settings, not a constant.

## The 0x0030 Record (12 words, fixed)

```text
001c 0030 000c 0000 [x0] [x1] 00ff [flag] 000c 0000 0030 001f
```

`b0` and `b1` of RFC 0009 are `x0` and `x1`, the left and right edge of the
fragment. `flag` was observed as `0x0002` when a line break was inserted inside
a cell in Ichitaro 33, but it is always 0 in older documents, so it cannot be
used to join fragments into logical cells.

An empty fragment of width ≤ gap at the right edge of the table (for example
`(118,120)` in a table of width 120 whose last cell ends at 116) occupies the
position of the right border and is not a cell. It may appear on some physical
lines and not on others in the same table.

## Logical Cell Reconstruction

For a fragment `c` on physical line `L_i`:

1. if the previous physical line `L_{i-1}` has a fragment `c'` with the same
   `(x0, x1)`, and
2. the span covering `c'` has `style` 0 (no rule below),

then `c` continues the logical cell of `c'`. Otherwise `c` starts a new logical
cell.

When `L_i` has no `0x0010` record, each fragment inherits the `style` of the
fragment with the same coordinates on `L_{i-1}`.

In older documents a horizontal rule can appear as a physical line of its own
(a line with no fragment in the affected columns); condition 1 then separates
the cells naturally.

## Cell Stringification

The meaning of a fragment's text depends on whether it ends with `0x000a`:

- with `0x000a`: paragraph end;
- without `0x000a`: soft line break; the text continues in the next fragment of
  the same logical cell.

Ichitaro's plain-text export (cell strings, line-break replacement character
`R`) turns a logical cell into one line as follows:

1. concatenate the fragments in order, replacing `0x000a` with `R`;
2. if the last fragment ends with `0x000a`, do not emit that `R`; if it does
   not, emit one `R` as if an empty trailing paragraph existed;
3. do not emit leading empty paragraphs (paragraphs with no text, including
   paragraphs that hold only an object anchor).

Example (`gov-a.jtd`):

```text
fragments:  "商号(名  称)"+0x000a  /  ""            → 商号(名  称)R
fragments:  " 印紙貼付欄"+0x000a                    →  印紙貼付欄
fragments:  "ないでここに貼ってく" / "ださい。"+0x000a → ないでここに貼ってください。R
```

## Correspondence with the ODT Export

In the ODT produced by `SaveDocument(…, 22)`, `table:table-row` is a logical
row and `table:table-cell` a logical cell. In `gov-d.jtd`, the cells
`住所又は勤務先` (r1) and `（電話　－　）` (r2) are separate `table:table-row`
elements, while DocumentText stores both as fragments with the same coordinates
`(44,144)` on consecutive physical lines 8–11. All spans of line 8 have
`style=0x08`, lines 9–10 have `0x00`, and the algorithm above separates the two
cells. `rowspan` is not used in the observed range.

ODT column widths (cm) are not proportional to DocumentText coordinates within
one document (30 units = 3.11 cm versus 16 units = 1.94 cm in `gov-d.jtd`). The
coordinate unit is the character grid, not a physical length; see the next
section.

## Table Coordinate Unit (decoded, `synth-11-table-30col.jtd`)

A 2×2 table in a document whose line length is set to 30 characters has total
width 120 and cells `(2,58) (60,116)`; the same table with the default 40
characters per line has width 160 and cells `(2,80) (82,158)`. The coordinates
scale with the character count, so the unit is **one quarter of a character
width** (1 character = 4 units; the border and margin are 2 units each, i.e.
half a character). Ichitaro places tables on the character grid, so column
widths can be converted to character counts in this unit. This answers the
"physical unit of the coordinate values" gap of RFC 0009.

| Code | Meaning | Status |
| --- | --- | --- |

| 0x000c | Page break | decoded |
| 0x000a | Paragraph end (`decoded:false` in RFC 0009) | decoded |

## Selectors of the 0x0001 Inline Record (additions)

RFC 0003 treats selector `0x0003` as the ruby base text. In real documents it
also appears on headings and evenly-spaced words without ruby, such as
`電子証明書発行申請書` or `会社法人等番号`. `0x0003` is the general form of
"decorated body text"; it is ruby base text only when a record with selector
`0x0082` follows immediately. Inline records with selector `0x0000`/`0x0001`
whose content is a single control code (`0x0002`, `0x0008`) are anchors of
figures or frames and are not body text.

## LayoutBoxText and Footnote Streams

`LayoutBoxText` (bodies of layout frames, i.e. text boxes) and `Footnote`
(footnote bodies) use the same `SsmgV.01` container as `DocumentText`. Header
word `w[5]` (the low word of `0000 000a`) is the segment count, followed by that
many segments of `TextV.01` + region length + region.

| Stream | Segments | Region content |
| --- | --- | --- |
| DocumentText | 1 | Body |
| LayoutBoxText | number of frames (`gov-c`: 10 = number of `draw:text-box` in the ODT) | One body per frame; paragraph and table records are identical to the body |
| Footnote | 1 | Footnote bodies; in a document without footnotes only an inline "Note" with selector 0x0001 (the template placeholder) |

Segments are found by scanning for the `TextV.01` magic; the region length is
in UTF-16 units including records, as in the body. The two words after
`TextV.01` are the region length. Each segment can be parsed with the paragraph
and table parser of RFC 0009/0010 unchanged. In all 10 frames of `gov-c.jtd` the
paragraph text matches the ODT `draw:text-box` content (compared without empty
lines and tabs; in frames that contain a table the ODT enumerates cells as
paragraphs, so the number of empty lines differs).

Ichitaro's plain-text export (format 10) does not include layout frame bodies.
The anchor of a frame is presumed to be the selector-0x0001 inline with content
`0x0002` in the body together with the `LayoutBox` stream; the correspondence is
not decoded.

Selector-0x0001 inlines also appear in the body as generated text such as
footnote numbers (`*1`), and the plain-text export includes them. They therefore
cannot be hidden wholesale; only the trailing "Note" entry of the Footnote
stream is special-cased.

### Footnote Stream Entry Structure (decoded, `synth-09-footnote-single.jtd`)

Observed in a document with one footnote added through the Ichitaro 2023 GUI:

```text
Body (DocumentText):
  …後述）  [001c 0000 …]  [001c 0001 0007 0000 0000 0001 001d] *1 [001e 0005 0000 0001 001f]  。 000a

Footnote:
  [001c 0000 …] [001c 0001 … 0001 001d] *1 [001e …] 用語物理行 (line): … 対応する。 000d
  [001c 0000 …] [001c 0001 … 0001 001d] Note [001e …]  (default template entry, no 000d)
```

- The footnote number in the body is a selector-0x0001 inline preceded by a
  class-0x0000 context marker.
- One entry of the Footnote stream is: `0x0000` marker → `0x0001` inline (the
  number, same string as in the body) → body → `0x000d`. `0x000d` is the entry
  terminator and does not occur in the body stream.
- A trailing "Note" entry from the template is always present, even in
  documents without footnotes.
- Body markers and footnote entries can be paired by the number string. The
  `FootnoteLink` stream holds the explicit link table (next section).

### FootnoteLink Stream (decoded, `synth-10-footnote-multi.jtd`: 5 footnotes on 3 pages)

```text
header, 6 words: 0001 0001 0000 [size] [count] 0000
entries, 15 words × count:
  001a  next  prev  0000  pos  ffff  ffff  0100  next  prev  num  page  index  ffff  next
```

| Field | Meaning |
| --- | --- |
| pos | Position (in words) of the footnote marker (`0x0000` context record) inside the body region |
| num | Sequence number within the page (1-based); matches the body numbers `*1`, `*2` |
| page | Page number (0-based) |
| index | Sequence number within the document (0-based) |
| next/prev | Indices of the neighbouring entries (0-based; `ffff` at the ends) |

Observation: `pos` = 0x0291, 0x043d, 0x062f, 0x07af, 0x08bb each equals the
position immediately before the `[001c 0000 …]` marker in the body. With
per-page numbering `num` is 1,1,2,1,2, matching `*1,*1,*2,*1,*2` in the body.
The `0x0000` record at the head of each Footnote entry also carries the
document-wide index (0x0000, 0x0001, …).

## Impact on RFC 0009

- "Physical unit of the coordinate values": decoded (quarter character width).
- "`0x0010 w4=0x008f` sub-entries `[tag, v1, v2, v3]`, formula not decoded":
  `v3` is the span width, `v2` the style (rule below), positions accumulate as
  above. The sub-entry count equals `n_cells − 1` only when there is no rule
  below the last cell; in general it is the number of spans.
- "`0x000a` decoded:false": decoded as paragraph end.
- "`0x0000 len=12` precedes ruby/inline segments": consistent; the same
  `0x0000` record precedes the footnote marker inline.
- The `w7`/`w10` discussion of RFC 0009 is not contradicted; see the note under
  sub-entry `0x0026`.

## Known Gaps

- The **enumeration order** of cells in Ichitaro's cell-string export. It is
  not a plain row-major order and is not decoded. This does not affect text
  extraction; 3 of the 9 government documents match the export in order, the
  others match as a multiset of non-empty strings.
- fmt 1 span lists (`gov-a.jtd` has 4-word spans with tags `0x14`, `0x16`,
  `0x24`, `0x27`) are mapped correctly by the origin search, but the structure
  has not been confirmed independently.
- The meaning of sub-entry `0x0004`.
- The meaning of `flag` in `0x0030`.
- The relation between `0x0026` indentation and RFC 0009's paragraph-style
  hypothesis.
- The `Frame` stream and the anchor correspondence of layout frames.

## Verification Method

The same document was exported through Ichitaro's COM automation
(`JXW.Application`, `Application.Run(macro, 3)`) as `.jtd`, `.jtdc`, plain text
(cell strings) and ODT, and the reader output was compared with the text export
(multiset of non-empty strings; exact order where possible) and, for
`LayoutBoxText`, with the ODT. The synthetic documents were generated by macro
through the same interface.

An independent pure-Python reader implementing this RFC (`jtdlib`: OLE
container, `.jtdc` decompression, paragraph/table/footnote/layout-frame
parsing) and the corpus generation and verification scripts are published
separately.

The analysis, the reader and this text were produced by the author working
interactively with Anthropic's Claude. The observations, the Ichitaro-generated
reference data, and the verification were carried out and checked by the
author; nothing in this RFC derives from Ichitaro or filter source code or from
decompilation.
